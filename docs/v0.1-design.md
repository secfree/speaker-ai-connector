# Speaker AI Connector — Design Doc

## Goal

Let children access AI freely with voice, without a screen.

## Problem

Children should be able to talk to an AI assistant on demand, but giving them a phone or computer is undesirable — they will drift into games or videos. A Bluetooth speaker paired to a desktop OS (macOS or Windows) is screen-free and limited to audio, which fits the constraint.

The remaining gap: when the speaker turns on and connects to the computer, an adult still has to walk over, open the AI's voice mode, and start a new conversation. The child cannot do that themselves, which defeats the "free access" goal.

## Solution

A small cross-platform desktop app — **Speaker AI Connector** — that runs in the background (menu bar on macOS, system tray on Windows), watches for a specific Bluetooth speaker connecting, and on connect automatically:

1. Opens a realtime voice session to a configured AI service (Gemini Live in v1).
2. Captures audio from the speaker's HFP mic and streams it to the service.
3. Plays the response audio back through the speaker.

When the speaker disconnects, the app tears the session down. Next connect starts fresh.

Every input utterance and every AI response is recorded to disk as a WAV clip, grouped by session, so a parent can review past conversations in the app's Sessions view.

A session can also be started **manually** from the menu bar when no speaker is connected — primarily a developer/debug affordance so the AI pipeline (audio capture, VAD, Gemini Live, playback) can be exercised end-to-end without depending on Bluetooth hardware. A manual session uses whatever the OS default input and output devices are at the moment it starts (typically the built-in mic and speakers).

### Why a realtime API, not a browser

Earlier drafts of this design opened `chatgpt.com` in a browser and clicked the voice button via injected JS. That path is fragile (selector drift, login persistence, per-browser scripting permissions) and platform-specific (AppleScript on macOS, no clean equivalent on Windows). Realtime voice APIs (Gemini Live, OpenAI Realtime) take speech in and stream speech out over a single WebSocket — no browser, no selector, no cookie. They are also platform-agnostic, which matters now that Windows is a first-class target.

The browser path is retained as **Phase 3** for the Claude-via-web case (Anthropic does not currently ship a realtime voice API), but it is deferred indefinitely.

## User flow

1. Parent installs Speaker AI Connector on the Mac or Windows PC and grants the required permissions (Bluetooth, Microphone, autostart).
2. Parent opens the app once, picks the target speaker from a list of paired Bluetooth devices, enters a Gemini API key (stored in the OS credential store), and enables "Start at login".
3. Parent closes the app — it keeps running in the menu bar (macOS) or system tray (Windows).
4. Child powers on the speaker. The speaker auto-connects (standard Bluetooth pairing behavior).
5. Speaker AI Connector detects the connection, opens a Gemini Live session, and starts relaying audio.
6. Child talks; AI responds through the speaker.
7. Child powers off the speaker. Speaker AI Connector detects disconnect and closes the session.
8. Parent can later open the app's Sessions view to browse past sessions and listen to any input or response clip.

## Architecture

**Two-layer split:**

- A shared **Rust core** that owns everything platform-neutral or close to it: the audio pipeline, VAD, the Gemini Live WebSocket client, the coordinator state machine, and configuration. Built as a `cdylib`/`staticlib` with a stable C ABI (or via `uniffi` / `swift-bridge` / `csbindgen` for higher-level bindings).
- A **thin native UI shell per platform** that owns the tray/menu-bar surface, the settings window, OS permission prompts, autostart registration, and the platform-specific Bluetooth event source. The shell calls into the Rust core for everything else.

```
+-------------------+        +-------------------+
|  macOS shell      |        |  Windows shell    |
|  (SwiftUI app)    |        |  (WinUI 3 app)    |
|  - menu bar       |        |  - system tray    |
|  - settings UI    |        |  - settings UI    |
|  - IOBluetooth    |        |  - Win BT APIs    |
|  - SMAppService   |        |  - Task Scheduler |
+---------+---------+        +---------+---------+
          |                            |
          +-------------+--------------+
                        |
                +-------v--------+
                |  Rust core     |
                |  - coordinator |
                |  - audio (cpal)|
                |  - VAD (libfvad)
                |  - Gemini Live |
                |  - config      |
                +----------------+
```

### Components

#### 1. Bluetooth watcher (platform shell)

Classic-Bluetooth connect/disconnect events for *already-paired* devices, filtered by the configured device address. This stays in the platform shell because the underlying APIs are OS-specific and don't generalize cleanly:

- **macOS:** `IOBluetooth` — `IOBluetoothDevice.register(forConnectNotifications:)` and `device.register(forDisconnectNotification:)`.
- **Windows:** `Windows.Devices.Bluetooth` (WinRT) — enumerate paired devices, subscribe to `ConnectionStatusChanged`.

The shell pushes normalized `BTEvent { connected, address, name }` values into the Rust core over the FFI boundary. The core debounces (default 5 s) to avoid double-launching on brief Bluetooth drops.

> **Note:** `btleplug` is BLE-focused and not the right fit here — Bluetooth audio speakers use classic BT (BR/EDR), and connection-status events for paired classic devices are best read from the OS APIs above.

#### 2. Audio pipeline (Rust core, via `cpal`)

`cpal` for capture from the default input (the speaker's HFP mic) and playback to the default output. 16 kHz mono `i16`. Both macOS (CoreAudio) and Windows (WASAPI) are first-class `cpal` backends.

Force-default-output helper (set the OS default output device to the speaker on connect) is needed on some macOS configurations and probably some Windows ones too — implemented in small platform-specific Rust modules (`coreaudio-rs` on macOS, `windows`/WASAPI on Windows) and gated by a settings toggle.

#### 3. VAD relay (Rust core, via `libfvad`)

Wraps `libfvad` (the maintained WebRTC VAD fork). Gates the upload stream: silence forwards no frames, speech opens the gate with a small pre-roll, sustained silence closes it. This is the turn-taking signal — no wake word, no push-to-talk — and it is also the cost gate (a left-on speaker accrues no API spend during silence).

Single binding in the core, identical on both platforms.

#### 4. Gemini Live client (Rust core)

`tokio` + `tokio-tungstenite` (rustls-tls-native-roots) for the WebSocket. Streams gated PCM up at 16 kHz mono i16; routes received 24 kHz mono i16 audio frames to the playback sink. Surfaces typed errors (`NoApiKey`, `AuthFailed`, `Network`, `SafetyBlocked`, `Other`) up to the shell for menu-bar display.

**Default model:** `models/gemini-2.0-flash-live-001` — flash tier for kid-voice turn-taking latency.

**Safety settings (child-appropriate floor — decided in M5):** all four Live API harm categories block at the lowest probability tier:

| Category | Threshold |
|---|---|
| `HARM_CATEGORY_HARASSMENT` | `BLOCK_LOW_AND_ABOVE` |
| `HARM_CATEGORY_HATE_SPEECH` | `BLOCK_LOW_AND_ABOVE` |
| `HARM_CATEGORY_SEXUALLY_EXPLICIT` | `BLOCK_LOW_AND_ABOVE` |
| `HARM_CATEGORY_DANGEROUS_CONTENT` | `BLOCK_LOW_AND_ABOVE` |

Paired with a system instruction that asks for short, simple, friendly responses and gentle refusal of unsafe topics. Revisit in M7 against real kid-voice prompts — if false positives turn the speaker into "I can't help with that", relax to `BLOCK_MEDIUM_AND_ABOVE` per category as needed.

#### 5. Coordinator (Rust core)

State machine: `Idle → Launching → SessionActive → TearingDown → Idle`. Driven by two input event kinds from the shell:

- `BTEvent { connected, address, name }` — Bluetooth connect/disconnect for the configured target speaker (the primary trigger).
- `SessionCommand::{Start, Stop}` — a manual start/stop from the menu bar, valid only while no target speaker is connected. `Start` is rejected if the coordinator is already in a non-`Idle` state from a Bluetooth-driven session; if a target speaker connects during a manual session, the coordinator tears the manual session down and re-launches against the speaker so the user-visible behavior matches the "speaker connect = fresh session" rule.

The coordinator does not distinguish manual vs. Bluetooth-driven sessions internally beyond that gating — both run the same audio pipeline + Gemini Live session. Manual sessions inherit the OS default input/output (built-in mic and speakers, typically) since no force-default-output redirection happens without a target device. It emits `StatusEvent`s back to the shell for the tray icon and menu text, including a flag indicating whether the active session is manual so the UI can offer a "Stop session" item.

#### 6. Settings UI + persistence

**Per-platform shell** owns the UI:
- macOS: SwiftUI settings window, menu-bar `MenuBarExtra`. The menu-bar item also exposes a **Start session / Stop session** action for manually triggering a session against the OS default input/output (debug/test affordance — see [Solution](#solution)).
- Windows: WinUI 3 settings window, `NotifyIcon` tray. Same Start/Stop session item.

**Cross-platform config** lives in the Rust core, persisted via a small abstraction:
- **Non-secret config** (target device address, Gemini model, VAD sensitivity, silence timeout, force-default-output toggle): TOML file under the OS's per-user config directory (`~/Library/Application Support/SpeakerAIConnector/` on macOS, `%APPDATA%\SpeakerAIConnector\` on Windows) via the `directories` crate.
- **API key**: OS credential store — Keychain on macOS, Credential Manager on Windows — via the `keyring` crate.
- **Autostart**: platform shell — `SMAppService.mainApp.register()` on macOS, a Task Scheduler entry or `Run` registry key on Windows.
- **Session recordings**: separate from config — see [Session recorder](#7-session-recorder-rust-core) below.

#### 7. Session recorder (Rust core)

Persists every input and output audio clip on disk so a parent can review what was said in any past session.

- **Session** = one full coordinator session (`Launching` → `TearingDown`). Each session writes to its own directory under `~/Library/Application Support/SpeakerAIConnector/sessions/<session-id>/`, where `<session-id>` is the RFC 3339 UTC timestamp of session start (e.g. `2026-05-23T14-03-12Z`).
- **Clip** = one VAD-gated input utterance, or one Gemini Live audio response. Clips are stored as WAV (PCM, the same 16 kHz mono `i16` the pipeline uses) named `<seq>-<dir>.wav`, where `<seq>` is a zero-padded ordinal within the session and `<dir>` is `in` or `out`.
- A per-session `manifest.json` records the trigger (`bluetooth` / `manual`), start/end timestamps, target device address (if any), and an ordered list of clips with their directions, offsets from session start, and durations.
- The recorder lives in the core. It receives input frames from the VAD relay's gate-open stream (so silence is not recorded) and output frames from the Gemini client. Writes are incremental — the recorder does not buffer beyond the active clip.
- FFI surface: `list_sessions()` (metadata only, newest first), `list_clips(session_id)`, and `clip_path(session_id, clip_id)`. The shell plays clips through its native audio API (`AVAudioPlayer` on macOS) — raw PCM still does not cross the FFI boundary, only file paths.
- No automatic cleanup or retention cap in v0.1. The settings window includes a "Reveal Sessions Folder" action.

### `AIServiceProfile` abstraction

Stays as a Rust enum / trait in the core. v0.1 ships one variant — `GeminiLive { model }`. Phase 2 adds `OpenAIRealtime { model }`. The deferred web path becomes `WebBrowser { url, voice_trigger, signed_in_probe }` if it ever ships, and lives entirely in the platform shells (since browser automation is OS-specific anyway).

## Permissions required

| Permission | Why | macOS | Windows |
|---|---|---|---|
| Bluetooth | Watch connect/disconnect events | `NSBluetoothAlwaysUsageDescription` in Info.plist; system prompt | `bluetooth` capability in app manifest; system prompt |
| Microphone | Capture HFP audio from the speaker | `NSMicrophoneUsageDescription` in Info.plist; system prompt | `microphone` capability in app manifest; system prompt |
| Autostart | Launch on login | `SMAppService.mainApp.register()` | Task Scheduler entry or `HKCU\...\Run` registry key |
| Network | WebSocket to Gemini Live | (none on macOS for outbound) | `internetClient` capability |

The Mic permission is **this app's concern** in v0.1 (different from the older browser design, where the browser owned the mic).

## Non-goals

- Filtering / moderating what the child says to the AI. Out of scope; rely on the AI service's own safety settings.
- Multi-user / multi-speaker routing.
- Linux support. Possible if there's demand, but not v1.
- iOS / iPad / Android support.
- A2DP-only (no-mic) speakers — v1 requires HFP/HSP with a working mic.
- Wake word / push-to-talk — local VAD handles turn-taking.
- Content for distribution via the macOS App Store or Microsoft Store in v0.1. Sideload / direct download is fine for now; store packaging is a later concern (App Store sandbox + Bluetooth/Mic entitlements is non-trivial).

## Risks & open questions

1. **HFP mic quality.** Mono 8/16 kHz over HFP is acceptable on paper but unproven for a child's voice through Gemini Live STT. Verify on real hardware on both OSes before declaring M6 done.
2. **Audio routing.** Neither macOS nor Windows reliably switches the system default output to a freshly connected Bluetooth speaker in every configuration. Force-default-output helper is implemented per OS; default-on vs. default-off decided in M6.
3. **Speaker auto-reconnect reliability.** If the speaker fails to auto-connect on power-on, the child is stuck. This is a Bluetooth-stack problem, not something this app can fix — document working speaker models per OS.
4. **Session boundaries.** Disconnect always ends the AI conversation. Loses context across sessions but avoids the next connect silently continuing an old chat, which would be more confusing for a child.
5. **Login persistence is gone, but API-key handling replaces it.** A revoked or expired API key now produces the equivalent dead-end. Surface `"Gemini auth failed — check API key"` in the tray instead of retrying silently.
6. **FFI surface.** Keeping the Rust ↔ shell boundary small and typed is critical — every leaky type costs us twice (once per platform). Plan: `uniffi` or hand-written C ABI with a single `Event` enum in, `Status` enum out, plus a handful of config getters/setters. Avoid streaming raw PCM across the FFI boundary — audio capture and playback live entirely inside Rust via `cpal`.
7. **Native voice mode arrives later.** If Anthropic ships a realtime voice API, add it as another `AIServiceProfile` variant — no architectural churn.

## Roadmap

### Phase 1 — Gemini Live (v0.1, both OSes)

The path described above. macOS and Windows ship together, sharing the Rust core. UI shells are independent and can land at different tempos but neither OS ships until both have a working M5.

### Phase 2 — OpenAI Realtime API

Same shape (speech-in/speech-out over WebSocket). Adds a second `AIServiceProfile` variant in the Rust core; UI shells get a service picker. No new platform code.

### Phase 3 — Browser fallback (deferred indefinitely)

The original browser-automation path (open `chatgpt.com`/`claude.ai`, click voice button via injected JS) survives only because Anthropic does not currently ship a realtime voice API. If/when it does, this phase may be dropped entirely. If we ever build it, it lives in the platform shells (AppleScript on macOS, UI Automation / CDP on Windows) — the Rust core stays out of it.

### Open questions for Phase 1

- ~~Which mic does the speaker actually expose (A2DP-only vs. HFP/HSP with mic)?~~ **Decided:** v1 requires HFP/HSP-with-mic speakers. A2DP-only is out of scope.
- ~~HFP audio is mono 8/16 kHz — does that degrade Gemini Live's STT for a child's voice?~~ **Decided:** accept on paper, verify on real hardware in M6.
- ~~Cost ceiling.~~ **Decided:** local VAD gate — no audio sent during silence. Per-day cap deferred unless real usage shows it's needed.
- ~~Wake-word / push-to-talk.~~ **Decided:** local VAD handles turn-taking.
- ~~Safety controls: Gemini's safety settings are configured per request — pick child-appropriate defaults in M4, revisit in M6.~~ **Decided in M5:** all four harm categories at `BLOCK_LOW_AND_ABOVE` + a short, friendly system instruction. Revisit in M7 if false positives are a problem.
- Local VAD library. Candidates, roughly in order of cost-to-integrate:
  - **`cpal` RMS thresholding** — no dependency, a few lines on the capture callback. Cheapest, but level-based gates are noisy: HFP background hiss, the speaker's own playback bleeding into the mic, and a quiet child all confound a fixed threshold.
  - **WebRTC VAD (`libfvad`)** — small C library, four aggressiveness levels, runs on 10/20/30 ms frames of 8/16 kHz mono PCM — exactly the HFP format. Battle-tested, tiny, no ML model to ship. Builds cleanly under `cc` on both macOS and Windows. **v1 default.**
  - **Silero VAD** — small neural VAD (~1–2 MB), more robust to noise and non-speech sounds, runs via ONNX Runtime (cross-platform). Heavier to integrate; worth the cost only if WebRTC misfires in the actual room.
  - **Platform speech APIs** (`SFSpeechRecognizer`, Windows Speech) — full recognizers, not lightweight VADs; using them just for endpointing is overkill and would split the implementation per OS. Not preferred.

  Start with WebRTC VAD; fall back to Silero only if real-room testing shows WebRTC misfires on a child's voice or on speaker bleed-through.

## Milestones (v0.1 = Phase 1)

- **M1 — Rust core skeleton + Bluetooth watcher (both shells).** Rust workspace, FFI surface stubbed, macOS SwiftUI shell and Windows WinUI 3 shell each detect a chosen paired device connecting / disconnecting and log to console via the core. ~3–4 days.
- **M2 — Audio capture + playback round-trip via `cpal`.** Capture from default input, play to default output, end-to-end loopback on both OSes. ~2 days.
- **M3 — VAD relay using `libfvad`.** Gated upload stream; speech opens, silence closes. Unit-tested with recorded fixtures; verified on both OSes. ~1–2 days.
- **M4 — Session recording + history viewer.** Per-session directory of WAV clips under Application Support; "Sessions" view in the shell with click-to-play. Input clips wire in now (driven by the M3 VAD diagnostic); output clips wire in M5 alongside Gemini response frames. ~2 days.
- **M5 — Gemini Live WebSocket client + API key in OS credential store.** Real session over the wire, typed errors, child-appropriate safety defaults, output clips written through the session recorder. ~2–3 days.
- **M6 — Coordinator wiring + config persistence + autostart + tray/menu-bar UX.** Settings windows on both OSes, status surfaces, "Test now" button, `SessionRecorder` lifecycle driven by coordinator state. ~3 days.
- **M7 — On-hardware polish with real speaker and child voice on both OSes.** Audio routing decisions, VAD sensitivity defaults, README with tested speaker models per platform. ~2 days.

## Build

Rust toolchain (stable, 1.75+) on both platforms.

**Shared core:**
```
cd core && cargo build --release
```

**macOS shell:**
```
cd shells/macos
xcodegen generate     # XcodeGen; project.yml is checked in, .xcodeproj is not
open SpeakerAIConnector.xcodeproj
```
Links against `libspeaker_core.a` produced by the workspace build.

**Windows shell:**
```
cd shells/windows
# Visual Studio 2022 with the WinUI 3 / Windows App SDK workload
# Open SpeakerAIConnector.sln
```
Links against `speaker_core.lib` produced by the workspace build.

A top-level `justfile` (or `make`) wraps the three-step build (`core → macos shell` / `core → windows shell`) so contributors don't have to remember the order.
